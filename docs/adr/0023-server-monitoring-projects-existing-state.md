# M2 服务端监控只投影已有状态

M2 不新增交易状态机，也不把浏览器提醒搬成另一套自动交易运行器。API 进程启动一个独立观察者线程，只读取现有自动交易快照，把任务状态、事件生命周期和通知投递结果写入既有 `AuditEventStore`。

## 决策

服务端监控任务使用稳定 ID `server-monitoring`，持久化累计轮次、最近轮次、最近成功、最近错误、连续失败、下次可运行时间和 Webhook 投递结果。自动交易运行器使用稳定受观察任务 ID `auto-trading:crypto:BTC-USDT:1m`，复用既有心跳、成功、错误和运行状态，不复制评估逻辑。

任务调度只保留当前需要的两种语义：

- Crypto 为连续调度，下次可运行时间等于上次轮次加固定间隔。
- A 股任务复用现有市场日历，在盘前、午休、收盘和周末指向下一开市时刻。M2 不自动创建 A 股研究任务；只有真实任务接入时才消费同一函数。

事件身份由固定类别组成，例如未决委托、账户不一致、权限或风险暂停、行情阻断、后台连续失败、心跳中断和运行器停止。动态错误文本不参与 `incidentKey`。当前事件记录 `active / resolved`、发生次数、开启时间、最近观察时间、恢复时间、严重度、原因和下一步。

相同发生周期只生成一次开启投递和一次恢复投递。投递记录在网络调用前以稳定去重键写入审计账本，避免进程恢复后重复发送。恢复后再次发生会增加发生次数并形成新的去重键。

首个外部渠道是可选 Webhook，使用 Python 标准库和 `AIQT_MONITORING_WEBHOOK_URL`。Webhook URL 不进入 API、审计或页面；消息只包含脱敏事件身份、生命周期、严重度、说明和观察时间。投递失败被记录但不抛回自动交易运行器，也不改变交易、风险、授权、对账或审计状态。已有浏览器 Notification API 继续作为页面打开时的本地渠道。

只读 API `GET /api/operations/monitoring` 返回任务、受观察任务、当前事件、投递记录和渠道状态，并明确 `tradingActionsAvailable=false`。执行中心先显示状态、阻断原因和下一步，任务 ID、轮次及投递错误放在渐进披露区域；没有重启、评估、对账或委托按钮。

## 安全边界

- 服务端监控没有行情、AI、对账、重启、模式切换或订单方法。
- Webhook 响应不会被解释为命令。
- 未配置或配置无效时 fail closed，只保留持久事件和浏览器提醒。
- 普通 CI 与 Docker smoke 不配置交易凭据，不产生 Testnet 或 Production 外部写入。
- 当前 Testnet 后台监控不因 M2 开发或验收被暂停、重启或切换模式。

## 验收

M2 退出需要同时证明：

1. API 进程内的观察者在浏览器关闭时继续记录任务轮次。
2. 任务 ID、最近轮次、最近成功、最近错误、连续失败和下次可运行时间可跨服务对象恢复。
3. 未决委托、账户不一致、风险或权限阻断、心跳中断、连续失败和运行器停止产生稳定事件。
4. 相同发生周期不重复投递，恢复只投递一次，再次发生形成新周期。
5. Webhook 可选、URL 不外泄，失败不改变交易快照或事件审计。
6. API 和执行中心只读展示状态、原因、下一步及渐进证据。
7. Python、Web、生产构建、Docker smoke 和真实页面复验通过。

## M2 退出结论

截至 2026-07-28，上述七项均已有当前代码、自动测试和隔离 Docker 证据。服务端观察者与自动交易运行器独立运行；任务和事件由现有 SQLite 审计账本恢复；开启、恢复和再次发生的去重行为经过进程级服务重建测试；Webhook 的可选、无 URL 外泄和失败隔离经过确定性替身验证。

隔离 Docker 项目在显式清空全部交易凭据、`Paper / disabled` 状态下通过基础 smoke，API 重启后监控轮次由 `2` 增至 `3`，受观察任务仍可回读，`tradingActionsAvailable=false`，全部实盘与投单边界保持关闭。真实页面在 `1280 × 720` 下无横向溢出、控制台无错误或警告，并只执行了只读展开操作。

最终回归为 Python `774 / 774`、Web `1075 / 1075`，生产构建与 API/Web Docker 镜像构建通过。M2 不要求配置真实 Webhook 地址；未配置状态是受支持的 fail-closed 路径。Issue #22 仍包含 M3 至 M6，因此不因 M2 完成而关闭。
